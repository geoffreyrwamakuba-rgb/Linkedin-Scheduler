The same 10 GB reads slower in Spark as 10,000 small files than as 40 large ones. That's the small files problem.

Every file costs something before a single row is read. It has to be listed, opened, and its Parquet footer parsed, and each one tends to become its own task. At 1 MB a file, that overhead is most of the work.

How tables end up like this:
→ Streaming or frequent small appends, each writing a few files
→ Partitioning by a column with too many values, so every partition holds a sliver
→ Many parallel tasks each writing their own small file

How to check: DESCRIBE DETAIL on a Delta table returns numFiles and sizeInBytes. Divide the size by the count. If the average file is a few MB, you've found it.

How to fix it on Databricks:
→ OPTIMIZE rewrites small files into larger ones. The target is autotuned, 256 MB for tables under 2.56 TB.
→ Optimized writes and auto compaction stop it coming back.
→ Partition by fewer, lower-cardinality columns.

Adding workers spreads those 10,000 file opens across more machines, but each one still pays the per-file cost, so it's the files that need fixing.
